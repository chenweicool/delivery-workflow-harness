# Delivery Workflow 报告治理与下一阶段完善

> 定位：Delivery Workflow 是交付事实的生产者；Harness Client 只是向外部平台发送报告的可替换对接方。  
> 状态：方案决策稿，暂不直接扩展统计字段。

## 1. 核心结论

**不要向最终用户开放核心报告格式、核心字段映射或手工编辑 JSON 的能力。**

一期报告中的以下字段是 Workflow 的产品契约，不应由用户在设置页自定义：

- `schemaVersion`
- `reportId`
- `generatedAt`
- `demand.startedAt`
- `demand.completedAt`
- `demand.owner`
- `demand.url`

用户能做的是在创建 Workspace 时录入业务事实，例如需求链接和负责人；Workflow 在确定的生命周期节点生成报告。用户不能在 Console 中编辑已生成的报告，也不提供“上传任意 JSON”的产品入口。

原因很直接：如果用户可以调整字段定义、时间口径或生成后的内容，跨需求、跨团队的统计将失去可比性，最终只能得到“自报数据”，不能得到交付度量。

## 2. 报告、Workflow 与 Harness Client 的边界

```text
用户录入业务事实
        ↓
Delivery Workflow
  - 固定 schema
  - 生成/校验报告
  - 记录本地回执
        ↓
DeliveryReportSink（抽象传输接口）
        ↓
Harness Client / HTTP / Kafka / 其他平台适配器
        ↓
外部统计平台
```

### Workflow 负责

- 定义和版本化 `delivery-report` schema。
- 固定生成时机、字段口径、校验规则和幂等标识。
- 维护 Workspace 内的需求事实与交付生命周期。
- 在上报前校验报告，保留上报回执。
- 不依赖任何内部平台地址、账号、私钥或前端路由。

### Harness Client 负责

- 获取平台访问凭据。
- 按外部平台协议发送已生成的标准报告。
- 处理传输失败、重试和回执。
- 可被 HTTP、Kafka、文件投递或其他 Adapter 替换。

### 外部平台负责

- 校验支持的 `schemaVersion`。
- 认证上报身份、记录上报人和上报通道。
- 按 `reportId` 和内容 Hash 幂等接收。
- 将“客户端上报数据”与未来的“服务端验证数据”区分展示。

## 3. 本机 JSON 是否可信

本机 JSON 必然可被有本机文件权限的使用者改写，因此不能把“文件不能被改”作为安全假设。

当前 v1 可保证的是：

- 正常产品路径不会允许用户编辑已生成报告。
- Workflow 在固定时点生成，并以 `reportId` 幂等上报。
- 服务端保存原始 JSON、Hash、上报用户和接收时间，便于审计。

当前 v1 **不能**保证的是：

- 恶意本机用户修改 JSON 后再调用 Client 上报。
- 用户伪造需求开始/结束时间。
- 本机管理员窃取令牌后构造虚假报告。

因此，v1 的数据定位应为“Workflow 生成并由已认证用户提交的交付事实”，可用于流程验证和趋势观察；不应用于绩效考核、奖惩或高风险经营决策。

## 4. 报告字段治理规则

### 4.1 核心字段冻结

- `schemaVersion: "1.0"` 的字段语义一经发布不改变。
- 如需改变核心字段的名字、类型、必填性或统计口径，发布新的 schema 版本，而不是覆写 v1。
- 平台仅接受显式支持的 schema 版本。

### 4.2 扩展字段受控开放

保留 `extensions`，但不把它当作任意统计字段入口。

- 可允许团队或 Adapter 写入命名空间扩展，例如 `extensions.integration`。
- 平台默认只存储、不纳入正式统计口径。
- 某个扩展字段经过产品评审、样本验证和版本设计后，才提升为正式指标或新 schema 的核心字段。

### 4.3 生成后不可变

- `delivery/delivery-report.json` 首次完成时生成；重复执行返回同一报告。
- 对需求链接、负责人等确有更正需求时，不直接覆盖交付报告。
- 后续可增加“更正事件/新版本报告”机制，保留原始事实、原因、操作者和时间。

## 5. 下一阶段：Workflow 优先完善项

### P0：先固化报告生产者

1. **Schema 注册与运行时强校验**
   - 在 Workflow 内维护 schema registry。
   - 生成和上报前都进行 JSON Schema 校验。
   - 禁止未知核心字段和不支持版本直接进入正式上报。

2. **报告生成边界收紧**
   - 仅由 `dw report complete` / Console 完成动作生成。
   - 不增加“选择本地 JSON 上传”的能力。
   - 上报动作只读取符合 schema 的 Workflow 正式产物。

3. **报告来源信息**
   - 在受控扩展中补充 Workflow 版本、生成器版本、Workspace 标识和生成模式。
   - 供排障和版本兼容使用，不直接作为业务统计维度。

### P1：提高数据真实性与可追溯性

1. Workspace 生命周期事件日志：创建、负责人/链接变更、完成、上报、重试。
2. 对报告做规范化序列化和 Hash，回执记录请求结果与报告 Hash。
3. 平台增加报告详情与审计轨迹，展示原始报告、上报身份、接收时间和幂等结果。
4. 明确数据等级：`client-reported`、`workflow-verified`、`server-verified`。

### P2：正式统计前的增强

1. 当报告用于正式管理指标时，由平台参与记录关键事件：需求开始、完成确认、人员身份映射。
2. 引入服务端签发的 Workspace/需求标识或一次性上报凭据，减少离线伪造空间。
3. 将 Token 保存迁移至操作系统凭据库，并补充撤销、刷新、设备变更能力。
4. 对高风险统计增加抽样复核、异常检测和人工确认。

## 6. 当前不做的事项

- 不开放用户自定义核心 JSON 字段或字段映射。
- 不把 Harness 平台实现、内部地址或 Client Secret 写入开源 Workflow。
- 不在当前阶段将交付报告用于个人绩效或自动化奖惩。
- 已完成飞书真实需求链接跳转验证；当前优先收敛 Workflow 报告治理，而不是继续扩大页面功能。

## 7. 验收标准

下一阶段完成后，应满足：

1. 用户只能录入业务事实，不能通过正常 UI 改写核心报告。
2. 每份正式报告都能明确回答：由哪个 Workflow 版本、哪个 Workspace、何时生成、由谁上报。
3. 新增统计字段不会悄然改变 v1 历史数据的含义。
4. 更换 Harness/HTTP/Kafka 对接方不需要改动报告生成逻辑。
5. 平台能够区分普通客户端上报与未来服务端验证的数据等级。
